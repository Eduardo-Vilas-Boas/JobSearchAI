# 0005 — Continuous integration

## 1. Running the checks on GitHub

**Intention:** a reviewer pointed out that the tests only ran in the local pre-commit hook.
Nobody else could see that they ran, they could be skipped with `--no-verify`, and they
always ran on a machine that already had the database, the virtual environment and the
downloaded models. A check on a clean machine, with its result visible on GitHub, shows the
project installs and passes its tests from scratch.

**Spec changes:**
- GitHub Actions runs the same checks as the pre-commit hook (ruff lint, ruff format check,
  the full test suite without the live ATS tests) on every push to `main` and every pull
  request. A newer push to the same branch cancels a run still in progress.
- The database tests run against a Postgres container started next to the job, the same
  `pgvector/pgvector:pg16` image and credentials as `docker-compose.yml`, so the test
  setup needed no change.
- Dependencies are installed from the lock file (`uv sync --locked`), so CI fails if
  `uv.lock` is out of date with `pyproject.toml`.
- The guard's model (about 700 MB) is cached between runs. Its cache key comes from
  `guard.py`, where the model's commit is pinned.
- A README with the CI status badge was added. The repository had no README before.

**Findings:** not yet measured: how long a first run takes (no cache), how long a cached run
takes, and whether every test passes on Linux as it does on macOS.

**Open questions:**
- On Linux, `torch` from PyPI brings its CUDA libraries (several GB) although the guard runs
  on CPU. Installing the CPU-only build would make CI faster, but needs a change to how
  `torch` is resolved in `pyproject.toml`.
- Once the guard moves to Meta's gated Prompt Guard 2, CI will need a Hugging Face token
  stored as a repository secret, or those tests will fail there.
- The LinkedIn tests that read real captured pages are skipped in CI, since those pages are
  gitignored. Only the hand-written fixture is tested there.
